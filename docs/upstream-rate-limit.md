## 一、错误指纹：两种 429 必须分开

| 文案                                                                | 来源     | 含义                                                                         |
| ------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------- |
| `Reached overall message rate limit ... reset in N seconds/minutes` | 上游     | 账号级消息限流，本文对象                                                     |
| `rate limited by local gate ... reset in N seconds`                 | 本地闸门 | hint=16~17s 是令牌桶排队超 `gateMaxHold`(15s) 的指纹；更大值是闩剩余时间透传 |
| `failed_precondition: Your daily usage quota has been exhausted`    | 上游     | 配额耗尽，与限流是不同错误，不要混入限流分析                                 |

上游 hint 显示格式：剩余 <60s 报精确秒数，≥60s 报 `floor(分钟)`（"reset in N minutes"）。**整分钟文案是显示取整，真实 deadline 比显示值最多晚 ~59s**——本地闩若按 `now + N×60` 设置会系统性提前放探针。

## 二、触发：分钟桶计数，账号级口径

- 拒绝时上报的隐含 deadline（拒绝时刻 + hint）几乎全部落在分钟边界：新窗口 66 条轨迹中 52 条 mod60 ∈ {59, 0, 1}（本地时钟看是 :59~:00，上游时钟快 ~1s）。stderr 闩事件同分布（265/336 落 mod60=0）。
- 触发阈值**不由本代理的发送速率决定**：旧窗口发作前 60s 我方速率 14~~98/min，干净时段常年 40~~96/min（峰值 161/min）无事故；新窗口发作起点（23:39）前也无异常速率尖峰。"overall" 是账号全体消息口径，含本代理看不见的流量。
- 推论：不存在「本地 rpm 不超就安全」的确定阈值；本地整形的意义是控制发作期的形态与恢复速度。

## 三、封禁形态：分钟桶量化 + 概率执行

### 3.1 deadline = 所在分钟桶的末尾，桶内冻结

2026-09-14 04:32 起一段完整轨迹（相对秒 = 距首条拒绝；桶边界 B32=+25.0、B34=+145、B35=+205、B36=+265、B37=+325、B38=+385，即本地 :58.6 处）：

| 拒绝到达               | hint          | 隐含 deadline       | 所在桶        | deadline 落点      |
| ---------------------- | ------------- | ------------------- | ------------- | ------------------ |
| 0.0 ~ 14.5，连续 14 条 | 11~25s        | ≈25.0，**全程冻结** | B32           | B32 末             |
| 15.2                   | "1 minute"    | ≥75.2（真实≈85）    | B32           | **跳 B33 末**      |
| 96.2 ~ 105.6，16 条    | 39~49s        | ≈145，冻结          | B34           | B34 末             |
| 173.5                  | 31s           | 204.5               | B35           | B35 末             |
| 173.9 / 174.1          | "1 minute"    | ≥234（真实≈265）    | B35           | **跳 B36 末** ×2   |
| 235.9 ~ 252.7，18 条   | 12~29s        | ≈265，冻结          | B36           | B36 末             |
| 305 ~ 306，3 条        | 18~20s        | 325                 | B37           | B37 末             |
| 361 ~ 362，5 条        | 22~23s        | 385                 | B38           | B38 末             |
| 386.1，2 条            | **0 seconds** | =now                | B39（刚过界） | 新桶已爆、无追加罚 |
| 504.9                  | 0 seconds     | =now                | B40 末        | 同上               |

规则：**同一桶内无论再被拒多少条，上报 deadline 不动，就是该桶末尾**。旧版「每次被拒 +2.4s」被直接证伪——14 连拒 deadline 一步未动。

### 3.2 跳桶：惩罚按整桶阶梯前移

个别拒绝上报的 deadline 是**下一桶的末尾**（显示为 "1 minute"）甚至 +2 桶（"2 minutes"，新窗口 stderr 闩出现 8 次 120s + 3 次 119s）。同一秒的不同请求可报出不同 deadline（04:35:13 三条：B35 末 vs B36 末）——上游限流器是多分片的，各片计数与 deadline 各自漂移，这是 hint 偶发回退、跳桶时机不规律的原因。旧窗口拟合的「~25 次违规 +60s」应读作「每桶违规攒到一定量就跳一桶」的阶梯，平均斜率恰好 ≈2.4s/次；新窗口每桶跳桶时机不稳定（B32 第 14 条才跳、B35 第 2 条就跳），**跳桶触发条件未确定，大概率随分片计数漂移**。

### 3.3 执行是概率性的，不是全有全无

把每次上游发送按分钟画 S(成功)/R(拒绝) 序列，边际态下两者随机混排：

```
00:02  SSSSSSRRSRRSRRSSRRSRRRRSSS      (边际态，同秒混排)
04:38  SSSSSSSSSSSSSSSSSSSSSSRRRRRSSSSSSSSS
04:36  RRRRRRRRRRRRRRRRRRRRR           (全拒桶)
04:33  （零发送：本地闩 + 客户端静默）
```

直接量化：新窗口闩生效期内的上游发送 **1430 条中 790 条成功（55%）**、640 条被拒。旧文 EP3「967s/530 尝试/0 成功」是 600s hint 的**深度发作极端态**，不是通则；发作烈度低时上游对单条请求是一枚 Loaded dice，不是一堵墙。

### 3.4 封禁的滚动机制：每个新分钟桶再被打爆

长发作（昨晚最长 26min）不是单桶内罚时累积出来的，而是**违规尝试持续落入每个新桶，使新桶一开就超限**。证据链：

- 纯静默窗口后 ban 到期即解（02:09 → 03:26 间 77min 零拒绝）。
- B33 整桶我方零发送，B34 仍被拒——封禁延续不纯靠我方尝试，账号侧还有不可见流量或上游惩罚状态自身滚动。
- 刚过桶界的拒绝报 `reset in 0 seconds`：新桶计数已爆但无追加封禁，探针成本极低——这类拒绝不应触发长闩。

### 3.5 对旧「+2.4s/次」模型的处置

旧拟合的方向（发作期尝试越多、封禁越久）依然成立，但机制是阶梯不是斜坡：每桶违规 → 该桶全程拒绝；违规持续到新桶 → ban 滚一桶；攒量跳桶 → 多罚一桶。**实践含义不变：发作期每少一条上游尝试都值，但成本单位是「桶」不是「次」**——同一桶内多漏几条的边际成本低于把泄漏带进下一个新桶。

## 五、本地闸门实测（新窗口）

- **令牌桶整形正常**：客户端到达峰值 ~119/min > `max_rpm=80`，超出部分 2887 条被本地快败（429+Retry-After），未碰上游。
- **冷却闩有洞，但洞的形态值得细读**：闩生效期间仍有 ~645 次发送漏到上游被拒（全部上游拒绝的 ~75%），来源是「入睡前算好时刻表、睡醒不复检」的过期放行（睡到闩末的等待者在同一瞬间齐射 + 闩延长后旧时刻表打进新闩）+ 在途无法召回。每个闩窗口中位漏 6 条、最多 24 条。
- **泄漏意外充当了滴灌探针**：闩内漏发 55% 成功穿过——证明边际态下低速放行是有吞吐的，纯静默闩在概率执行的上游面前过度保守。

## 六、对本地设计的回写（v2，已落地）

> **实现状态（2026-09-14）**：第 1/3/4 条已按本节落地（`rategate.go` 滴灌闩 + `noteUpstreamSuccess` 解闩、`common.RateLimitReset` 桶界对齐、presold 令牌睡醒复检）；第 2 条实现时改取「Retry-After=闩剩余」让客户端睡到恢复时刻而非竞争滴灌槽；第 5 条观测落地为 stderr 日志（闩内拒绝 Info、解闩 Info）而非面板计数；第 6 条不变项保持。闩参数可配：`gate_max_hold_seconds`/`gate_drip_interval_seconds`/`gate_default_latch_seconds`（默认 15/8/60）。

1. **二元闩 → 滴灌闩**。闩内不是零放行，改为低节拍放行探针（建议 1 条 / 5~10s 量级，可配）：边际态大部分探针成功；**任一上游成功立即解闩**（需在成功路径新增 `noteUpstreamSuccess` 钩子，当前只有失败路径）。深封态代价是每分钟几条被拒探针；证据表明封禁去留不由这几条决定。探针被拒 → 按 hint 刷新闩；hint=0 的拒绝不延期。
2. **闩内不再睡到闩末**：等待者只在滴灌槽空闲时放行，槽位占用时按「距下一槽」秒数快败（Retry-After ≤ 槽间隔），客户端退避天然落在槽位节奏上；排队预算（gateMaxHold 语义）不变。
3. **分钟文案 hint 向上取整到上游桶界**（本地 :59 边界）再设闩："1 minute" 的真实 deadline 是下一桶末（60~119s），`now+60s` 最多低估 59s，探针提前撞墙白送拒绝。
4. **睡醒复检不变量**：放行决策必须在真实发送前一刻按当前闩/桶状态做出，不能按入睡时快照——这是 645 条闩内漏发的根因，滴灌化后同理（睡眠者醒来须重新按滴灌节奏排队或快败）。
5. **观测缺口**：`noteUpstreamError` 只在延长闩时打日志，闩内不延期的拒绝和全部成功在 stderr 隐身；应给「闩内上游拒绝/成功」计数，作为发作期仪表盘信号。
6. **不变**：令牌桶持续限速、`>gateMaxHold` 快败、闩内冻结桶防齐射（滴灌化后冻结语义变为「滴灌节拍」而非满桶）。

## 七、噪声与未决

- 跳桶触发条件未确定：分片计数阈值、违规强度、还是概率事件，外部不可分辨。
- 被拒尝试是否计入下一新桶的计数未确定；B33 零发送 B34 仍爆说明封禁延续至少部分与我方尝试无关（不可见流量或上游状态机自身滚动）。
- 深度发作（hint 数百秒）的阶梯结构只有旧窗口 EP3 一例，上限 10min 的说法未再验证。
- 账号「不可见份额」未量化；若同账号还有其他客户端在线，本文全部「我方速率」口径都只是下界。
