# CLIProxyAPI 问题谱系调研：对 devin-2api 的适用性分析

> 调研对象：`github.com/router-for-me/CLIProxyAPI`（多上游 × 多协议的 OpenAI/Gemini/Claude/Codex 兼容反代，~51k star）。
> 语料：全部 2,878 个 issue（75 open / 2,803 closed，编号至 #5753）+ 1,589 条 PR 元数据（409 merged，其中 ~216 条 fix）+ 220 个高互动 issue 的评论全文 + 浅克隆源码 `/tmp/cliproxyapi-src`。
> 语料副本：`outputs/cliproxy-research/`（`meta/`、`bytheme/`、`issues/*.jsonl`、`CONTEXT.md`）；分组报告 6 份：`report-error-taxonomy.md`、`report-thinking-replay.md`、`report-cloak-quota.md`、`report-tool-calls.md`、`report-stream-lifecycle.md`、`report-schema-hygiene.md`、`report-source-design.md`、`report-longtail.md`；实验记录 `EXPERIMENTS.md`（两批，第二批修正了第一批的 schema 结论）。
> 方法：8 个主题 subagent 分桶精读（流生命周期 / 工具调用 / thinking 与签名与 usage / 配额与认证 cloak / 客户端契约 schema / 源码机制研读 / 长尾 657+360 条标题扫描），再用 `cmd/probe` 对 Devin 上游做 30+ 组对照实验验证「他们的坑在我们上游是否存在」。
> 铁律：CLIProxyAPI 是多 OAuth 凭据池 + 冷却调度 + 跨协议翻译；devin-2api 是单 token × Connect-RPC `GetChatMessage` → OpenAI Responses（含 WS）/ Chat Completions / Anthropic Messages。**他们的问题不自动等于我们的问题**——凡「不适用」均给出理由；凡「适用」均对照到具体文件行。

## 〇、一句话结论

CLIProxyAPI 一年的修复史本质是「把上游协议的真实行为逐条发现并内化为状态机」：终态枚举、错误分类、模型 ID 语义、传输活性、回放载荷校验，每一项都先以**挂起 / 静默截断 / 误导性 503** 的形式暴露。devin-2api 的泵 + 单写者 + 截断检测+debuglog 架构方向已被证明是对的；第二批调研（源码机制 + 长尾+schema 卫生）新确认的缺口集中在：①`pumpUpstream` 终帧丢弃 + 泵协程泄漏（真实缺陷）；②非流式路径零字节等待被前置网关杀；③schema `$defs`/`$ref` 与裸属性 map 被上游确定性拒绝；④HTTP 层指纹（connect-go UA）与版本 pin 无逃生门；⑤「流建立成功 ≠ 安全」的 bootstrap 窗口缺重试环；⑥token 静默失效无自愈；⑦解码层静默丢弃面（unknown item/server tools/`response_format`/`document` 块）无观测。

## 二、CPA 核心教训 → 我们的对照状态

### 2.1 流式生命周期（最高价值主题）

CPA 把流分成 8 个阶段，每阶段是不同故障类：**建连→响应头→HTTP 200→首个真实 payload→正常流→终态事件→socket 关闭→干净 EOF**。他们的修复史证明这些不能共用一套策略。

| CPA 教训（代表 issue）                                                                                                                                                     | 我们的现状                                                                                                                                     | 判定                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 「流建立成功 ≠ 安全」：overload/auth 错误嵌在 200 流的握手事件里；`codex_executor_stream.go` 缓冲 ≤16 个事件探明后才提交下游头，可透明换路（#5115、#4642 open→该 PR 路线） | `streamCompletion` 有 pre-commit 首事件等待；但**首事件后、首内容前**没有重试环                                                                | **适用，是最大单点改进**——见行动 #1                                                                                        |
| 读到终态即收尾，不等 EOF（#852：Claude 上游 `message_stop` 后连接挂着 ping，读到 socket 关闭才停的 executor 无限挂起）                                                     | 我们**必须**读到 EOF：usage/`responseDimensionGroups` 在 stopReason 之后才到（实测 #15）。现行「EOF 无 stopReason = 截断报错」正确             | 已防住，但方向相反：他们等不到终态，我们等不到 EOF。看门狗兜底                                                             |
| 终帧/终止错误帧被缓冲挤掉（#5535 wsrelay stream_end 挤掉数据帧；#4904 关闭时未排空 pending error）                                                                         | `pumpUpstream`（devin.go）缓冲满时终止错误帧走 `default:` 丢弃；且数据帧裸 `frames<-` 无 ctx 分支——Recv 取到 ctx.Done 退出后泵协程永久阻塞泄漏 | **真缺陷（低概率）**：「已发 stopReason + 消费停滞 + 断流」→ 断流被吞报成正常完成；修法=终止帧阻塞投递 + 全发送带 ctx.Done |
| 终态合成不依赖可选字段（#852 根因①：`message_stop` 被 `if usage.Exists()` 门控）                                                                                           | `finish()` 无条件写终态                                                                                                                        | 已防住                                                                                                                     |
| EOF 无终态 = 显式截断错误而非伪造完成（#4904/#3996；我们实测过合成 stop 会让 Codex 当完成）                                                                                | `response_decoder.go:155-162` 已实现                                                                                                           | 已防住                                                                                                                     |
| 客户端断连不污染上游健康（#4820/#4787/#4819）                                                                                                                              | `result=disconnected` 单列，无冷却层                                                                                                           | 已防住                                                                                                                     |
| keepalive 与数据同写循环（#4047 心跳切开 SSE 事件）                                                                                                                        | 单写者 pump 架构                                                                                                                               | 已防住，建议补字节不交错测试                                                                                               |
| 非流式 keepalive 先提交 200 → 上游失败只能带内报错（#2973/#4782）                                                                                                          | 非流式路径 `collectFinalMessage` 全程零字节；connect 阶段最坏 600s×3                                                                           | **真缺口**：前置网关 60s 超时会先杀连接；可选 `\n` keepalive（代价=提前提交 200）                                          |
| 上游私有帧透传下游（#5171 keepalive 帧进事件流）                                                                                                                           | Connect 是 typed 帧非 SSE，无同构风险                                                                                                          | 不适用                                                                                                                     |
| WS 控制帧被大写阻塞饿死（#5734 pong 走 WriteControl 绕锁）                                                                                                                 | 我们的下游 WS 端需核对 ping 路径                                                                                                               | 待核对 `internal/app/websocket.go`                                                                                         |
| 压缩流误读 → 静默空流（#1837 gzip SSE）                                                                                                                                    | Connect-RPC 非此形态；等价物「200 但零内容」已有 EOF 校验                                                                                      | 已覆盖                                                                                                                     |

### 2.4 错误分类 / 配额 / 认证（单 token 下的裁剪版）

CPA 最大的反复事故簇是「冷却/负状态与上游现实脱节」（156h 粘性冷却、reset 不复活、sleep 穿越）。**我们无冷却层，天然免疫**；要保持的元规则：**任何引入的负缓存必须带 TTL 或到期自动失效**。

### 契约级回归测试包（防重构退化）

- `message_start` 首发、终态一锤定音（usage 帧不得改写）、无孤儿 `content_block_stop`、流式与非流式 usage 字段集一致、并行 tool_calls 的 call_id 配对、`content:null/[]/missing` 三形态。
- 「thinking→tool_use→tool_result→user」三拍夹具端到端回放（含 redacted 与缺签名）。
- 终态集合断言：`response.completed`/`failed`/`incomplete` 后零额外事件。
- keepalive 与 chunk 同时就绪时字节不交错。
- 上游发完 stopReason 后挂住不 EOF → 看门狗收尾路径。

### 明确不做（证据显示不适用）

- **CPA 式深度 schema sanitizer**：上游除 `$defs`/`$ref` 与裸属性 map 外全容忍（实测 #14/#21-23），只做这两条最小归一化，不抄全套管线。
- **签名 provenance/检测矩阵**：swe-2-max 不校验签名（实测 #7-8）；保留 `sealed.` 白名单即可。
- **剥离末尾未应答 call / 末尾 assistant prefill 合成**：上游容忍（实测 #5）。
- **多凭据冷却/轮换/亲和全套**：单 token。
- **模型族枚举字符串匹配判定能力**：用能力位（`supports_*`）已是对的。
- **`metadata.f` 改稳定值**：真实 CLI 每请求随机 732-hex（实测 #29-30），`randomHex(366)` 是复刻——改稳定反而是偏差。
- **下游头透传上游**（CPA `passthrough-headers`/凭据 `headers."$"`）：泄客户端指纹，无收益。
- **Merkle LCP 会话亲和**：单 token 无选路；`deriveSessionIDs` 够用（source-design §5.2）。
- **payload 规则引擎整套**：上游是 proto 非 JSON，gjson 规则操作不了；只取「字段开关表」思想（行动 #30）。

## 四、元教训（写给未来的维护者）

1. **「流建立成功 ≠ 安全」是反代的第一性原理**。CPA 花了 #3476/#4642/#5115 三个迭代才收敛到 bootstrap buffering；我们的 pre-commit 等待是对的一半，差「建立后、首内容前」的重试环。
2. **处置异常历史的优先级**：按 ID 修复 > 降级为文本 > 丢弃 > 整请求失败 > 伪造 ID/结果。CPA 的 #5375（伪造 ID 永久 wedge）和 #5682（翻译器/校验器自打架）都是反向教材。
3. **静默是排障天敌**：静默丢字段、静默 Debug 级失败、静默 token 失效——CPA 一半 bug 是「静默丢/改」被客户端异常行为暴露后才定位。我们的 debuglog 是优势，剩下三个静默点（dropped items、quota 采样失败、unauthenticated）提到 Warn 即可。
4. **负状态必须有复活路径**：CPA 一整簇 stale-cooldown 事故源于「写了一个永不自动失效的标记」。我们的 TTL 缓存模式天然正确，任何「记住失败」的设计都必须自带 TTL/对账。
5. **可选字段的缺省值是协议语义**：「没写就不发」在两个默认值相反的 API 之间等于改语义（#5555 的 901s/3.3MB 垃圾参数是单字段缺省造成的）。
6. **广告面、校验面、执行面共用一份能力源**：CPA 反复出现目录承诺与执行拒绝不一致（#4463）；我们的 capability bits 已同源，加「广告即可用」往返测试钉死。
