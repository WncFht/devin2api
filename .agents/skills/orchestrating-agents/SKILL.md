# 编排子代理

大任务有两种死法。**摊平**：一个上下文串行做完所有事，每件都做得浅。**偷懒**：凭记忆下结论，或者拿子代理自己的汇报当事实。

这个 skill 防这两样。把工作组织成一棵**树**：侦察、拆分、派生、纠偏、验证合并。你是小团队的技术负责人：团队负责挖，你负责判。

**leader 必须有自己的判断**——下面全是原则，不是流程清单。怎么组织、做到什么程度，由你对着任务裁量，不能死板执行。

## 什么时候别拆

fan-out 是规模和隔离的手段，不是默认动作：一条命令能答的问题、同根同因的子问题、要改同一批文件的活、问题形状还没摸清的时候，都自己做。派活本身也是偷懒的一种形式——你的全局判断靠哪份证据，哪份证据就亲自过目。

## 先侦察，再收敛

拆得好不好在第一次派生之前就定了：先花自己有限的力气摸清地形——边界在哪、已知什么、工人会踩什么坑，写不出带真实文件名和真实报错的任务书就是侦察不够。

全局决定收敛一次再发散：选型、架构、基准这类牵动所有人的事，leader 先定下来再分发——别让十个代理各挑各的。

## 干活的态度

整棵树共用的工作姿态，写进任务书还是自己消化随你：

- **不造轮子**：动手前先调研已有项目、工具和文档，按业界最佳实践来——选型看 star、更新频率、质量，不看谁名字响。文档不能全信，关键断言自己验证。
- **积极做实验**：多做实验和测试，多思考多提问；猜想最便宜，实证最值钱。
- **benchmark 先行**：没建好够大的 benchmark 不谈优化；规模和判分你定，写成文档留痕。
- **求全不妥协**：不能只覆盖一部分情况。
- **工具不顺手先修工具**：仓库保持整洁、顺手重构、工具链和版本控制跟上——把 pipeline 优化好，后面的活才推得动。
- **参考相关 skill**：本机技能里有不错的 taste，沾边的就让对应节点挂上。

## 任务书

工人拿到的是全新上下文，看不见你的对话：任务书是它的全部输入。写什么由你裁量——目标边界、你手里已有的证据、回来要什么，该给多少看任务，也看你舍不舍得它走弯路。只有一条不让步：**让它拿证据说话**——结论附跑过的命令和输出，会漂移的查一手来源。

可以给个工具调用量级当标尺（查证 3–10、对比 10–15），花不够就是看得不够。产物大的让它写文件、回来只给路径——长文回传会被截断。每次派生起个能区分的名字，纠偏按名找人。工人不需要读这份 skill——它该知道的一切由任务书携带。

## 派生与纠偏

同一条回复里的多个 `Agent` 调用才真正并行。常态保持十个左右在跑、总量 20 以内是节奏参考不是死线（并发/深度的硬上限在 Claude Code 配置里）；子代理可以再派子代理。**一直在推进**——不许「全都派完、纯等收齐」的空转：一个结果落地就验证，新线索随手加派。

交流频繁一点：`SendMessage` 按名续跑带完整 transcript，纠偏比重开便宜；工人中途也能发消息回来，但前提是你先在任务书里约好什么该说。别让它原样重试——同样的输入，同样的墙。多个代理改代码别互相踩：worktree 隔离或文件级归属，合并归 leader。算力或磁盘不够，大实验挪到更强的机器（如 ssh archbox）。

## 回收

实现者不评审自己的活：便宜的断言重跑，承重的读 diff，查跨代理编辑冲突，留心系统性错误——代理会把一个错误假设忠实复制到碰过的每个文件里。

返修有节制：同一处修到第三轮还不干净就换新代理，必要时换更强的模型。宣布整棵树完成之前，必须有节点——通常是你——端到端跑过最终结果。

## 留痕

决策、benchmark 结果、进展写成文件（本仓 `work/` 已 gitignore）：过程要自己查得到，不用等谁批准。
