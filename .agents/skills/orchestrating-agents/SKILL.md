# 编排子代理

大任务有两种死法。**摊平**：一个上下文串行做完所有事——读代码、探路、实现、验证挤在同一个窗口里，每件都做得浅。**偷懒**：凭记忆下结论，或者拿子代理自己的汇报当事实，而不是看证据。

这个 skill 防这两样。把工作组织成一棵**树**：先亲自侦察，把任务拆成互相独立的子问题，每个子问题派一个子代理、附一份自包含的任务书，回收时亲自验证再合并。你是小团队的技术负责人：团队负责挖，你负责判。

## 什么时候别拆

fan-out 是规模和隔离的手段，不是默认动作。以下情况自己做：

- 一条命令、一个文件就能回答的问题。
- 子问题同根同因，或者要改同一批文件。
- 问题本身还没摸清——先侦察，形状清楚了再拆。
- 收益配不上成本：一棵忙碌的树，token 消耗大约是单线程的一个数量级。

派活本身也是偷懒的一种形式：你的全局判断靠哪份证据，哪份证据就亲自过目——读 diff、重跑命令。工人的汇报是主张，不是事实。

## 先侦察，再拆分

拆得好不好，在第一次派生之前就定了。先花自己有限的力气——几次阅读、一次真跑——摸清地形：边界在哪、已知什么、工人会踩什么坑。然后沿着你实际看到的缝切。

写不出带真实文件名和真实报错的任务书，说明侦察得不够。

## 任务书

工人拿到的是全新上下文，看不见你的对话。任务书是它的全部输入，必须自包含：

- 目标和边界——包括明确的「不许做」清单；
- 你手里已有的证据——贴报错原文、点文件名，别让工人重新发现一遍；
- 沾边的 skill 点名让它挂上（如「invoke golang-pro」）——工人自己的 skill 列表里就有，调用它比你在任务书里复述标准可靠；
- 约束，以及它回来时要给你什么。

证据规则写进任务书：每个结论附跑过的命令和输出，API / 参数 / 版本这类会漂移的东西必须查一手来源，禁止凭记忆作答。给个工具调用量级作标尺——查证类 3–10 次，对比类 10–15 次；花不够就是看得不够。

约定什么时候主动说话：卡住先问，别猜；发现方向错了立刻讲，别攒到交报告。产物大的写进文件、回来只给路径——长文直接回传会被截断，等于白跑半截。

工人不需要读这份 skill——它该知道的一切由任务书携带，不由文件继承。每次派生起个能区分的名字，后面纠偏按名找人。

## 派生与纠偏

同一条回复里的多个 `Agent` 调用才真正并行，跨回复就变成串行。按每波 3–5 个派发：结果到了评审就能跟上，冲突在树还小时就暴露。

子代理可以再派子代理——某个子问题展开后自己长出新的一层时，让那个节点往下拆。并发与深度的上限交给 Claude Code 配置（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`、`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`），本 skill 不管数目。

树是活的，不是「派一批、等收齐」。一个结果落地就验证，新线索随手加派，跑偏的立刻 `SendMessage` 改向——按名字续跑，带着完整 transcript，纠偏比重开便宜。交流是双向的：工人中途也能发消息回来，但前提是你先在任务书里约好什么该说。别让它原样重试——同样的输入，同样的墙。代理多了就在 `work/` 下记个台账，一行一条——扛得住 context 压缩。

## 回收

实现者不评审自己的活。对每个回来的结果：便宜的断言重跑一遍，承重的断言读它背后的 diff，检查和其他代理的编辑有没有撞车，留心系统性错误——代理会把一个错误假设忠实地复制到它碰过的每个文件里。

返修有节制：发现的问题发回原代理，同一处修到第三轮还不干净就换一个新代理，必要时换更强的模型——新读者能看见旧上下文已经合理化掉的问题。

宣布整棵树完成之前，必须有某个节点——通常是你——端到端跑过最终结果：把应用跑起来、把最初的故障现象重放一遍、读完合并后的完整 diff。
