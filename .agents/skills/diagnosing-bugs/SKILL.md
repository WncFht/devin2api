# Diagnosing Bugs

疑难 bug 的纪律。只有明确说得通时才跳阶段。

探索代码库时读 `CONTEXT.md`（若存在）建立相关模块的心智模型，并查看你动手区域的 ADR。

## 脱敏

本 skill 会让你展示命令、输出和抓取的产物。**先把每个秘密脱敏**：原地写 `<REDACTED>`。回路要对着环境变量搭，让凭据留在环境里而不是出现在你展示的内容里。抓取的产物带 auth 头：只引用带信号的行。

脱敏后的输出不够诊断这个 bug 时，明说出来并问用户。

## 阶段 1：搭反馈回路

**这是本 skill 的本体。**其余都是机械活。如果你有一个对这个 bug 会变红的**干脆** pass/fail 信号，你迟早找到原因——二分、假设检验、插桩都只是消耗这个信号。如果没有，盯代码盯再久也救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构造回路的方法，大致按此顺序

1. **失败测试**，打在够得着 bug 的任意 seam 上：单元、集成、e2e。
2. **Curl / HTTP 脚本**，对着跑着的开发服务器打。
3. **CLI 调用**，喂 fixture 输入，拿 stdout 对已知好的快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/console/network 断言。
5. **重放抓取的 trace。**把真实网络请求 / payload / 事件日志存盘，隔离着重放过代码路径。
6. **一次性 harness。**拉起系统的最小子集（一个服务、mock 依赖），一次函数调用打到 bug 代码路径。
7. **属性 / fuzz 回路。**bug 是「有时输出错」就跑 1000 个随机输入找失败模式。
8. **二分 harness。**bug 出现在两个已知状态（commit、数据集、版本）之间，就把「在状态 X 启动、检查、重复」自动化，好拿去 `git bisect run`。
9. **对照回路。**同一输入分别过旧版与新版（或两份配置），diff 输出。
10. **人在环 bash 脚本。**最后手段。必须人来点，就用 `scripts/hitl-loop.template.sh` 驱动_人_，回路照样结构化。抓到的输出回流给你。

回路搭对，bug 就修好了九成。

### 拧紧回路

把回路当产品打磨。有了_一个_回路之后，**拧紧**它：

- 能不能更快？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 信号能不能更尖？（断言具体症状，而不是「没崩」。）
- 能不能更确定？（钉住时间、给 RNG 播种、隔离文件系统、冻结网络。）

30 秒的 flaky 回路比没有强不了多少；2 秒的确定性回路才叫紧，是排障超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发循环 100 次、并行化、加压、收窄时序窗口、插 sleep。50% flake 的 bug 是可调试的；1% 不是——一直抬复现率抬到可调试为止。

### 真的搭不出回路时

停下来明说出来。列出试过的方法。问用户要：(a) 能复现的环境的访问权，(b) 脱敏后的抓取产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。**不要**在没有回路的情况下进入假设阶段。

### 完成判据：一个能变红的紧回路

阶段 1 完成的标志是回路**够紧**且**能变红**：你能报出**一条命令**（脚本路径、测试调用、一条 curl），它已经**至少跑过一次**（展示调用与输出，脱敏后），并且：

- [ ] **能变红**：它驱动真实的 bug 代码路径并断言**用户的那个症状**——这个 bug 在就红、修好就绿。不是「跑下来没报错」；它必须能_逮住这个特定 bug_。
- [ ] **确定性**：每次跑结论相同（flaky bug：按上文钉住的高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可跑**：你能无人值守地跑；要人进环只能走 `scripts/hitl-loop.template.sh`。

如果你发现自己在命令还不存在时就读代码建理论，**停：直接跳假设正是本 skill 要防的那个失败。**没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路。看着它随 bug 出现而变红。

确认：

- [ ] 回流产出的失败模式是**用户**描述的那个，不是恰好附近的另一个失败。诊断错 bug = 修错 bug。
- [ ] 失败多次运行都能复现（非确定性 bug：复现率高到能对着调试）。
- [ ] 你已抓到确切症状（错误信息、错误输出、变慢的耗时），后面的阶段才能验证修复真的对症。

### 最小化

变红之后，把复现削减到**仍然会变红的最小场景**。输入、调用方、配置、数据、步骤**一次只砍一个**，每砍一刀重跑回路，只留对失败承重的部分。

为什么要做：最小复现压缩阶段 3 的假设空间（剩下要怀疑的活动部件更少），并且成为阶段 5 干净的回归测试。

完成判据是**每个剩余元素都承重**：再砍掉任何一个，回路就变绿。

复现**且**最小化之前不许往下走。

## 阶段 3：提假设

先产出 **3–5 个排序过的假设**再测其中任何一个。只产一个假设会锚死在第一个看似有理的想法上。

每个假设必须**可证伪**：写明它的预测。

> 格式：「如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。」

写不出预测，这个假设就是 vibe：丢掉或磨尖它。

**测之前把排序清单给用户看。**用户常有领域知识能立刻重排（「我们刚部署了改 #3 的变更」），或知道哪些假设已被排除。便宜的检查点，省大量时间。别堵在这等；用户不在就按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的某个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，环境支持就用。一个断点顶十条日志。
2. **定点日志**，打在能区分假设的边界上。
3. 永远不「全量打日志再 grep」。

**每条调试日志都带唯一前缀**，如 `[DEBUG-a4f2]`。收尾清理就是一条 grep。没标记的日志会活下来；带标记的必须死。

**性能分支。**性能回归时日志通常是错的工具。改为：先立基线测量（计时 harness、`performance.now()`、profiler、查询计划），再二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

回归测试**写在修复之前**，但前提是存在**正确的 seam**。

正确的 seam 是测试能以调用点处的真实形态驱动**真实 bug 模式**的缝。若唯一可用的 seam 太浅（bug 要多个调用方而测试只能单调用方、单元测试复现不了触发 bug 的链条），在那里写回归测试只会给假信心。

**若没有正确的 seam，这本身就是发现。**记下来：代码库架构让这个 bug 锁不死。为下一阶段标记出来。

有正确 seam 时：

1. 把最小化复现变成那个 seam 上的失败测试。
2. 看它失败。
3. 打上修复。
4. 看它通过。
5. 拿原始（未最小化）场景重跑阶段 1 的反馈回路。

## 阶段 6：清理

宣布完成前必须做：

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或「无可用 seam」已记录）
- [ ] `[DEBUG-...]` 插桩全部移除（`grep` 前缀）
- [ ] 一次性原型已删除（或挪到明确标注的调试位置）
- [ ] 被证实正确的那个假设写进了 commit / PR 信息，让下一个排障者学到东西
